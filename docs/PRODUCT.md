## Purpose and brand

Give an existing personal/coding agent a dedicated computer, let its owner see
and control that same screen, and teach procedures the agent can reuse.
**Sendtry Computer** is the product name. `computer-mcp` remains the technical
repository/CLI. David's Sendtry identity provides the mark, warm paper canvas,
white surfaces, salmon actions and ink text. This product has its own runtime and
data; Sendtry's delivery backend and Piblo's bot/billing layers are not dependencies.

The code and generic operator skill use [MIT](../LICENSE), selected by David
on 27 October 2026. [Sendtry brand terms](../TRADEMARKS.md) are separate. The
repository remains private during [publication preparation](PUBLICATION.md),
and the npm manifest retains `private: true`. Source notices are recorded; exact
binary-image notices, public release policy and managed lifecycle remain open.

## Experience

The console has eight working views:

| View           | Owner's job                                                                                    |
| -------------- | ---------------------------------------------------------------------------------------------- |
| Screen         | Watch the real guest screen, take/release control and open the offline practice task           |
| Tasks          | Assign bounded work to a named connection, inspect its report and record your own verdict      |
| Files          | Browse the contained workspace and read/save bounded text files                                |
| Terminal       | Execute/cancel a focused guest command and inspect exit status, deadline and truncation        |
| Teach & skills | Teach, search, review, prepare an agent request and export a completed procedure               |
| Computers      | Inspect the registered catalog/default and copy owner create/start/open/use commands           |
| Connect agent  | Create/revoke named read/work access through safe host commands and install the operator skill |
| Activity       | Inspect sessions, control/tool time, outcomes and private local history exports                |

The flow is **create computer → connect agent → work together → teach a task →
optional agent video analysis → review → reuse**. MCP tools are capabilities. Skills are procedural instructions.
A taught skill depends on those capabilities and its owning computer; exporting
it does not create a new permission, install anything, or blindly replay actions.

Control lives in one sticky session bar with the current computer and connection.
The available action follows runtime state: Take control, Take over or Release.
Keyboard focus follows a replaced control. Recording and Finish remain reachable
when scrolling; Release stays unavailable until the demonstration is saved.
No lease means control is free; an agent/human lease
shows who controls mutations. The owner's explicit Take control action revokes
agent work. View-only remains useful while the agent works. Recording starts only
with owner control; a persistent recording bar returns to review/save. The saved
skill lists missing parameters and supports a reviewed `SKILL.md` download.
**Try with new inputs** prepares a plan or task request with supplied inputs, pinned to
the saved review and owning computer/workspace. The owner previews/copies it into
their existing harness. Inputs clear when the panel closes or the owner leaves
Skills; preparation does not start execution. A pending proposal blocks use.

Onboarding uses the exact host paths generated by the trusted CLI. They travel
only to its owner session and are never exposed by agent credentials. No API
keys appear in copy/download output. The console reports actual guest capabilities
and lease state; it does not claim that a specific harness is connected.

Connect agent follows three selectable steps: create a named connection, install
the operator skill and start working. Its connection check opens a prefilled
tracked task for named work access. The dedicated Tasks view owns custom
name/goal/outcome/scope and assignment selection. Read/plan and explicit legacy
paths remain available. Saving a named task persists its explicit requirements;
copying never dispatches an agent. Reports are agent claims; owner checks are
separate recorded verdicts after inspecting actual artifacts. Teach trial inputs
remain local to the copied request, not automatically stored in the assignment. See [task assignment](TASKS.md).
Client selection provides the configuration format,
local project skill path and official setup/skills guides for Claude Code, Cursor
and Codex. Other stdio clients receive a neutral path placeholder. The request
preview pins both computer/workspace UUIDs; work checks create/read a uniquely
named synthetic file and run `pwd`, while read checks observe without a lease.
Existing different file contents must not be overwritten. Control/recording
state tells the owner when to release, save Teach or wait. Nothing is marked
connected or completed merely because configuration/skill/request was copied.
Only one setup stage is visible at a time, with the exact configuration behind a
disclosure and local next/back step selection. Stage navigation records no
installation or task completion; it changes only the open owner view.

Skills highlights Demonstrate → Understand → Review → Try new inputs from its
current recording, selected saved skill, pending proposal, stale revision and
open review. A persistent **Finish demonstration** saves through the existing
Teach endpoint and returns to the saved skill. Evidence is expandable so the
procedure and expected result lead the review. Proposal uncertainties and discard
remain visible outside the collapsed evidence. Selecting a different saved skill
focuses the next-action heading, including on compact screens; refreshing the same
skill preserves the evidence disclosure. Finish requires the current owner's
control and is disabled during guarded requests. **Reviewed** is separate from
task verification. The guide says when a connected agent must receive an analysis
request; consent/copy is never presented as analysis in progress. It preserves
zero-step, deleted-video, interruption and unsaved-edit restrictions.

On compact screens Skills opens as a searchable library; selecting a saved task
opens its detail instead of stacking the library above a long review. **Back to
skills** retains the search and focuses the selected card. Reopening that same
unchanged revision preserves local review edits; choosing another skill,
refreshing or selecting a changed revision loads the saved data. Returning clears
prepared trial inputs and pauses the video. Desktop retains the adjacent library
and detail. Finish restores keyboard focus after the runtime state refresh.
Guarded actions remain disabled until a fresh metadata read completes. Older
poll responses cannot replace that state; an eight-second metadata deadline
shows an unavailable state and allows the normal reconnect loop to recover.
Recording name, goal and video choice stay fixed while Start is pending.

## Visual and interaction rules

Use light, quiet surfaces and one primary action per local task. Ink is text,
salmon is action/selection, and compact SVG icons identify the views. The
live Linux desktop retains its actual browser/OS appearance. No remote font,
analytics, cloud account, provider OAuth or model/chat UI is required.

The sidebar groups daily work, tools and setup/history. On narrow screens a
keyboard-accessible Menu exposes all views, closes with Escape and returns focus
to its trigger or the selected view heading. Panels stack,
configuration and instructions wrap, and keyboard focus remains visible. Polling
preserves skill search and focused list items when data is unchanged. Connection,
authorization, recording and interrupted states derive from the runtime. Owner
access failures explain the CLI recovery without exposing the existing host PC.
An unauthorized response locks the console, clears prepared requests/owner
metadata and focuses one recovery panel with generic host CLI instructions.
Late responses from the previous owner session cannot restore authorized views.
This presentation safeguard complements the runtime's authorization checks.
Running a terminal command makes cancellation reachable by keyboard and returns
focus to the command after completion/cancellation, unless the owner moved focus
elsewhere. Unsaved review errors also appear beside skill actions on compact
screens. A deleted video is labelled explicitly; its approved procedure remains
editable even without structured steps.
Action buttons use a darker Sendtry salmon for legible light text; decorative
marks and selected surfaces retain the original brand palette. Advanced tool
names sit behind an accessible disclosure so first connection remains focused.
Selected navigation/skills use a restrained coral edge; neutral badges, subtle
panel boundaries and neutral disabled controls keep state distinct from actions.
Compact control targets are at least 44 px high. The decorative coral
`#d06a54` comes from Sendtry's existing tokens/mark, while darker `#b95440`
supports light button text. Open-source distribution does not prescribe these
colors; branding and future code/asset licensing remain separate decisions.

The host's read-only `doctor` supports pre-creation prerequisite checks and
reports host space separately from measured space in an owned running guest.
It does not create computers, change the default Docker context, start stopped
guests or clean resources. Diagnostics are not an agent capability or proof of
successful client registration/task execution.

The practice task is a local form in the real guest browser, styled with the same
Sendtry palette. It demonstrates Teach and profile persistence offline; its
browser-local saved note is not a second workflow backend.

## Current boundaries

Portable host CLI does not mean portable guest OS. The implemented computer is a
Docker Linux guest; macOS/Windows native control or isolated VM guests require
separate adapters and explicit permissions. See [support](../README.md#platform-support),
[security](../SECURITY.md) and [validation](VALIDATION.md).

Teaching records bounded main-frame browser events plus file/terminal markers.
An optional guest-only, silent WebM video records the visible Linux desktop.
The owner can play/download/delete it and consent to sampled-frame analysis by
connected work agents. The connected vision harness reasons over images/trace
and submits a draft; the owner edits the procedure, expected result and notes
before publishing reviewed skill instructions. Drafts can be discarded without
losing prior approved edits. No model/chat gateway or automatic training is
included. Sampled frames may miss actions. Bounded guest `desktop_action` input
supports native windows; targets/focus need fresh screenshot verification, and
input delivery is not task success. Drag, clipboard, automatic blind replay,
skill imports and archives remain future work. See [Teach](TEACH.md) and
[desktop tools](DESKTOP.md).

The computer name is session context; Computers is the catalog route. Selecting
a CLI default never switches a running connection. Activity describes sessions,
rather than implying
verified people. Activity connects operational evidence to the same computer: declared client,
authenticated access, observation session, tool outcomes and control intervals.
The owner can filter and export metadata for later evaluation without exposing
commands, file data or video. Identity and time are deliberately described as
observed metadata, not verified people/models, billing or success certification.
Local retention and owner-readable exports replace any hosted analytics service.
Activity disables its filters and export/paging controls during an in-flight
request so a changed selection cannot appear with the previous totals. Session
selection applies to history, summary and the downloaded JSON together.
See [Activity](ACTIVITY.md).
